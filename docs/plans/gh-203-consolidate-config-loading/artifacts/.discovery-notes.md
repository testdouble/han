## The config contract and its consumers

- `han-core/references/config-rule.md` (canonical, 151 lines) plus 12 byte-identical vendored copies. Its "two
  probes and the personal read" section pins the mechanism per skill: directory probe, project-file probe, and a
  Read-tool call as the skill's first action (a probe cannot prompt or degrade; the personal file is the one lookup
  outside the project).
- `scripts/han-config-dir.sh` (repo root) symlinked as `han-*/scripts/han-config-dir.sh` in every plugin that carries a
  config-consuming skill. `scripts/han-config-dir.bats` enforces: exact probe text, exact grant text, and that each
  plugin can reach the script, over every SKILL.md carrying the probe. These tests will need to change with the sweep.
- `docs/configuration.md` says "Every Han skill reads both files on every run, so the overrides take effect without
  depending on the model remembering to look." A one-line "if you have not already this run" instruction changes that
  sentence's truth for chained skills (by design) and the doc must say so.
- `CONTRIBUTING.md` lines 181-182 ("Adding a skill" step 2) tell authors to copy the probe and grant from an existing
  skill. Must change with the sweep.
- `han-communication/skills/readability-guidance/SKILL.md` Step 1 resolves `writing-voice` from "either
  `.han/config.md` probe". It is the only consumer that resolves a value from the config inside an inline sub-skill;
  every other consumer applies config-rule.md itself.
- Precedent for the inline shape: `readability-guidance` and `explanation-guidance` (both carry the probe block AND
  are invoked inline, which is the double-load the issue describes). Precedent for machine-written skill-consumed
  context: `han-core/skills/project-discovery`.
- Long-form doc convention for inline-guidance skills: `docs/templates/coverage-rule.md#the-inline-guidance-variant`
  (TL;DR, Key concepts, When it is used ...). CONTRIBUTING step 3 points there.
