## Standards and guidance this change must respect

There is no `docs/coding-standards/` folder. Authoring standards live in
`han-plugin-builder/skills/guidance/references/skill-building-guidance/` (26 files), each carrying a `paths:` frontmatter
scoping it to `**/skills/**/*.md`. The four that bear on this work:

### `allowed-tools-AskUserQuestion.md` — a live conflict with the current skill

**`AskUserQuestion` must not appear in a skill's `allowed-tools`.** A Claude Code permission-evaluator bug
auto-approves it through the `alwaysAllowRules` path and returns empty answers without ever rendering the prompt. The
guidance cites upstream issues #29547 and #9846.

`.claude/skills/han-release/SKILL.md:16-18` currently lists `AskUserQuestion` in `allowed-tools`. The skill already
calls `AskUserQuestion` at Step 3d (the version-plan confirmation) and Step 7 (the pre-publish pause). This is a
pre-existing defect, and it lands directly on `D15`, which commits to a mandatory approval stop before the first tag
push.

### `allowed-tools-bash-permissions.md`

Each command prefix needs its own `Bash()` entry with a space before the wildcard. Narrower is better, but a skill that
uses many subcommands of one tool may take the broad form. The current list is:

```
Read, Edit, Write, Glob, Grep, Agent, AskUserQuestion, Bash(git *), Bash(gh *), Bash(jq *), Bash(which *), Bash(grep *), Bash(sed *), Bash(head *)
```

Nothing in it matches an invocation of the Claude Code command line, which `D3` makes the skill depend on.

### `context-injection-commands.md`

Context-injection probes run once at skill load and never prompt. A probe that is not auto-approvable hard-rejects and
stops the skill loading, and only the first failing command reports, masking every later one. Four constructs are
refused outright regardless of `allowed-tools`, including **command substitution `$(...)`** and **process substitution**.
Pipes and `&&` chains are allowed when every part is independently allowlisted or declared. This constrains how the new
prerequisite probe for the Claude Code command line (`D11`) can be written, and it interacts with `T1`'s recommendation
to resolve the executable rather than call a shell wrapper.

### `docs/semantic-versioning.md`

The repository's versioning policy. `D12` corrects it. Three places state the old scheme: line 103 ("the git tag for a
release tracks the **parent** version"), line 145 ("The release is tagged `v3.1.0`"), and the section "A note on
per-plugin tags and version constraints" (lines 148-156), which says Han does **not** need per-plugin tags and that "The
single suite tag `vX.Y.Z` is sufficient." `SKILL.md:146` reads this file to classify each plugin's bump level.

## Verified command behavior

Established during the specification interview and re-verified during its synthesis, at Claude Code 2.1.221, against
this repository and an isolated throwaway clone. The main repository was left untouched.

- `claude plugin tag [path]` accepts a path argument, so the run never changes directory. Flags: `--dry-run`,
  `-f/--force`, `-m/--message`, `--push`, `--remote`.
- It resolves the marketplace entry from `.claude-plugin/marketplace.json` and ignores the versionless Codex manifest at
  `.agents/plugins/marketplace.json`.
- Exit 0 on success; exit 1 on tag-already-exists-locally, dirty tree under the plugin folder, version disagreement,
  missing manifest, and bad path. **The exit status alone cannot separate a benign already-exists from a real failure.**
- It does **not** consult the remote. With the tag on the remote and absent locally, it planned to create it.
- Pushing against a remote that already holds the tag fails with `! [rejected] ... (already exists)` and leaves a
  divergent local tag. The rejection repeats identically, so pushing is not a recovery.
- `git tag -l 'han--v*' --sort=-v:refname` isolates the parent and does not match `han-core--v3.0.0`. It sorts correctly
  across double-digit versions.
