## Tech stack

- **Test:** `npm test` runs `find . -name node_modules -prune -o -name '*.bats' -print0 | xargs -0 bats`. Every `.bats`

## Script and test precedent

This is the load-bearing precedent for the two executed checks.

- **Invocation form.** `${CLAUDE_SKILL_DIR}/scripts/<name>.sh`, used across `han-github`, `han-coding`, `han-reporting`,
  and `han-plugin-builder`. Example: `han-github/skills/post-code-review-to-pr/SKILL.md:50`.
- **Tests sit beside the script**, same basename, `.bats` extension. `test/sanity.bats` states the convention in a
  comment: "Real script tests sit next to the script they cover (e.g. `scripts/foo.sh` alongside `scripts/foo.bats`);
  `test/` keeps only harness-level checks like this one."
- **Bats style.** `setup()` creating a `mktemp -d` sandbox, `teardown()` removing it, small helpers for parsing
  line-oriented `key: value` output. See `han-coding/skills/code-review/scripts/detect-review-context.bats` (311 lines).
- **Input validation form.** `han-github/skills/work-items-to-issues/scripts/upload-screenshots.sh` is the closest
  existing analogue to the design-image check: it reads `ui-designs/`, validates arguments with
  `"${1:?message}"`, guards with an explicit `[ -f ... ]`, runs `set -euo pipefail`, and constrains file types with an
  allow-list pattern at `:48` — `ASSET_EXT_PATTERN='(png|jpg|jpeg|gif|webp|svg|pdf)'` — carrying a comment at `:6-8`
  naming `planning-boundary-rule.md` as the source of that set. A check that needs the same allow-list has a working
  precedent to copy, including how the duplication is documented.

### How this repo handles one script needed by several skills

**Verified, and the first reading of it was wrong.** `han-coding` has four `detect-*-context.sh` scripts. Two of them,
`code-review/scripts/detect-review-context.sh` and `automated-test-planning/scripts/detect-test-context.sh`, are
byte-identical except for two comment lines that name each other as the copy to keep in sync. Their `.bats` files are
byte-identical at 311 lines. The other two, `tdd/scripts/detect-tdd-context.sh` and
`refactor/scripts/detect-refactor-context.sh`, are different tools doing different jobs, not drifted copies.

So the existing precedent is: **copy the script into each skill's own `scripts/`, add a mutual NOTE comment naming the
other copies, and keep them in sync.** It has held at two copies.

**A shared location is reachable but unprecedented for scripts.** `${CLAUDE_PLUGIN_ROOT}` is used today to reach outside
a skill directory: `han-communication` resolves `${CLAUDE_PLUGIN_ROOT}/references/readability-rule.md` and
`han-plugin-builder` resolves `${CLAUDE_PLUGIN_ROOT}/skills/guidance/references/`. No plugin-level `scripts/` directory
exists anywhere in the repo; every `scripts/` directory sits under a skill.

This is the open architectural question for the plan: the design-image check is needed by four skills in one plugin. The
precedent says four copies plus sync notes; the variable needed for one shared copy already exists and is already used
for `references/`, but not yet for `scripts/`.
